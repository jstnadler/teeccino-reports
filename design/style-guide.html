Philosophy

Warm, natural, editorial-with-structure. The rebuilt pages read as a scrolling brand story — hero → trust → benefits → flavors → how-to-brew → FAQ → reviews → cross-sell → founder → donation — not as a spec sheet.

The three moves
  • Warm & natural — cream / chestnut / gold neutrals with green benefit cues say "herbal, good-for-you, caffeine-free."
  • Editorial — Faricy New display headlines, uppercase letter-spaced eyebrows, generous whitespace, full-bleed hero, founder band.
  • Structured but soft — square-cornered media (radius 0) for crispness, offset by 999px pills and 12px content cards.
The one restraint
  • Berry red is a punch, not a paint. It marks action and top-level headings. It is never decorative, never a background field, never the fourth berry element in one viewport.
  • Chestnut is the workhorse. Across the 21 color schemes berry is the button in only 2; chestnut is the button in 11. Brown is the theme's majority voice.
Product truth that overrides any aesthetic call: Teeccino brews dark — coffee-colored, near-black in a cup, like cold brew. Never depict it pale, amber, or tea-colored in any creative, on any surface. Iced Teeccino is iced coffee, not iced tea.

Contrast note. Berry #B5404C on white is — — it passes AA for normal text but not AAA. Chestnut #6b3327 on white is — (AAA). Where a long run of body-adjacent text needs a brand color, chestnut is the safer choice; berry is for headings and buttons, which are large or reversed-out.

Color schemes

The theme ships 21 color schemes. Each one declares only CSS custom properties on a .color-<id> class; the background paint is applied separately to body. Sections pick a scheme; they do not pick hex values.

The single most common bug in this system: a section built without a color_scheme setting inherits scheme #1 (background-1) from :root — which means it silently renders berry. That is inheritance by accident, not a design decision. Always declare a scheme explicitly on a new section.
SchemeBackgroundTextHeadingButtonButton labelLink / 2° button

Read of the set: white backgrounds dominate (the schemes are overwhelmingly white or cream — plan color bands via CSS, never assume a dark canvas). Chestnut carries the majority of buttons; berry appears as the button in two schemes only; gold #e1b77e is the button on every dark/brown/teal/olive scheme, which is what keeps reversed sections from going muddy.

Shape & radius

The radius system is deliberately bimodal: media is square, chrome is round. Crisp editorial imagery against soft interactive affordances.

Ad-hoc radii in component CSS, by frequency: 999px (pills — by far the most used), 50% (circles/avatars), 0, 14px, 12px / 1.2rem (content cards), 0.8rem, 6px, 4px, 3px. When adding a component, land on one of these — do not introduce a new value.

This is the cohesion pattern to copy. Three surfaces — the PDP inline pill (campaign-sale-badge.liquid), the product-card corner ribbon (card-campaign-badge.liquid), and the shop-all card (shop-all-card.liquid) — are visually different by intent (a full pill is too heavy on a small card) but read one setting and share one gate (custom.discount > 0 + date). They cannot drift apart. Any future multi-surface visual signal should be built this way: one token, one gate, per-surface weight.

Usage rules

Do
  • Spec in tokens: var(--color-button), var(--font-heading-family), var(--page-width) — not hex and pixels.
  • Declare color_scheme explicitly on every new section.
  • Build color bands with CSS on a white canvas — the scheme set is white/cream dominant.
  • Reach for chestnut as the default brand hue; save berry for action.
  • Land new radii on an existing value (999 / 50% / 14 / 12 / 0.8rem / 6 / 4 / 3 / 0).
  • Design mobile-first and QA at 375 / 750 / 990 / 1440.
  • Keep media square; keep interactive chrome round.
Don't
  • Don't leave a section's scheme unset — it silently inherits berry.
  • Don't hardcode a hex when a scheme token exists; it will not follow a scheme change.
  • Don't add a fourth berry element to a viewport — accent volume matters as much as hue.
  • Don't assume a dark canvas is available; there is no dark-page scheme in general rotation.
  • Don't round product imagery or introduce a shadow on product cards.
  • Don't invent a new campaign color — use campaign_sale_accent.
  • Don't design around a product metafield without confirming it exists.
  • Never design away an allergen disclosure — it is a compliance fact, not stylable copy.

Known gaps & drift

Honest inventory. These are open items in the system as of this compile — documented here so a spec doesn't unknowingly build on top of them.

  • No --color-error token exists. Error text currently borrows --color-button, so a destructive/error message renders in the same hue as the primary action — a semantic collision. Needs a dedicated token.
  • Eyebrow treatment has drifted three ways. Live in the PDP CSS: Faricy Medium 1.3rem/0.12em, Montserrat 1.2rem/0.18em, and Assistant 1.1rem/0.2em — all doing the same job. One canonical eyebrow spec should win.
  • Off-palette green in the cart. .tc-cart__savings uses #1f7a1f, which is neither brand green (#3BAF4A / #2C7A38).
  • Cart title breaks the type hierarchy — it overrides Faricy New for Assistant, unlike every other site h2.
  • Cream surfaces are blocked on imagery, not taste. Of 147 catalog products, 21 are JPEG (opaque by format) — on a cream panel those render a hard white box behind the product photo. A cream drawer or cream card field needs an AssetSmith re-cut first.
  • Scheme sprawl. 21 schemes, several near-duplicates (e.g. two identical white/chestnut schemes with different IDs). Worth a consolidation pass before the set grows further.
  • A transparent-button scheme exists (scheme-6a5da08b…, button rgba(0,0,0,0)) — usable, but it produces an invisible primary CTA if applied without intent.
How to use this page. Spec against it, don't copy from it — cite the token, not the value. When a design needs something this page doesn't have, that's a design-system change: it gets spec'd here first, then ThemeSmith implements the token, then this page is recompiled from the theme. The theme is always the source of truth; this page is its readable face.
