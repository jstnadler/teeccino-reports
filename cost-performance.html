🧮 How cost is calculated — cost to operate each machine per hour

Unit cost = machine-hours per unit × cost to operate per hour. Operating cost/hr = operators × wage (human labor) + machine overhead/hr (electricity, maintenance, equipment). Because each machine runs a different crew size, its hourly labor already differs — the buildup below shows exactly how.

Machineavg opslabor $/hr+ machine oh $/hr= operating $/hrmach-hrs / unitlabor $/uoh $/utotal $/u

“avg ops” = average operators per run on that machine (from the schedule). “mach-hrs/unit” = machine run-time per unit produced. Overhead $/hr and its unit share stay $0 until utility/equipment costs are supplied in config.

📖 Glossary — what each term means & how it's calculated (new here? start with this)
The foundation
Unit
One finished sellable item (e.g. one bag or one box), as defined by the item's case size in the production schedule. Every "$/unit" figure is the cost to produce one of these.
Date range
The picker at the top of the page filters every section — KPIs, machines, variance, throughput, yield, batch, trend and the SKU explorer — to production runs whose actual production date falls in the window. Undated rows are excluded whenever a range is active.
Wage rate
The labor cost of one operator-hour, in dollars. Read from a single config value; every dollar on this page = hours × this rate. When the rate is a placeholder the figures are illustrative — the banner at the top always states the current status.
Standard (std)
The planned expectation — how long a job should take, from the schedule's planned figures. The benchmark we measure reality against.
Actual
What really happened on the floor — measured from actual run time, actual operator count and actual quantity produced.
Scope: labor only (v1)
Every number here is the labor cost of running the machines. It does not include ingredients, packaging, or facility overhead — those come in later phases once we have a validated cost source.
Cost & variance
Standard labor-hours / unit
The person-hours a unit should take. Comes straight from the schedule's "Labor Rate" column. operators ÷ planned units-per-hour
Actual labor-hours / unit
The person-hours a unit actually took. actual run time × operators ÷ actual units produced
Labor $ / unit (std $/u, act $/u)
Those hours turned into dollars. labor-hours per unit × wage rate
Efficiency variance (var %)
How far actual ran over (or under) standard, as a percentage. Positive = took longer than planned = money leaking. (actual − standard) ÷ standard × 100
$ over std (in range)
The total dollars that variance cost across everything produced in the selected window — the size of the leak, not just the rate. (actual $/u − std $/u) × units produced
Items over standard
How many finished goods ran costlier than their standard (actual > standard). The count worth investigating.
Quantity-weighted
When averaging across many runs, big runs count more than small ones — so the average reflects where the volume (and money) actually is. Σ labor-hours ÷ Σ units
Throughput & downtime
Run hours
Clock-hours the machine was running a job.
Operator hours (op hrs)
Total person-hours worked — run hours multiplied by how many operators were on the line. Two people for 3 hours = 6 operator-hours.
Units per operator-hour (u/op-hr)
Productivity: how many units one person produces in an hour. Higher = more efficient. units produced ÷ operator hours
Downtime % (DT %)
Share of running time lost to stoppages (changeovers, jams, breaks). downtime minutes ÷ total minutes × 100
Downtime labor cost (DT $)
The wages paid to operators while the line was not producing — idle-but-staffed time turned into dollars. downtime hours × operators × wage rate
Batch economics
Setup hours
The fixed labor to prepare a run before any units come off — estimated from the pattern of many runs (the part of the time that doesn't grow with quantity).
avg → max
The item's average batch size today vs. the largest batch it has been run at — the headroom for consolidating into fewer, bigger runs.
Batch-consolidation upside (est. $/yr)
Estimated yearly labor saving if the item ran at its larger batch size, because the fixed setup cost gets spread over more units. setup cost saved per unit × yearly volume
Yield & scrap
Finished-unit scrap
Whole sellable units thrown away. Rate-able because we know the good-vs-bad count for the same unit of measure.
Finished scrap %
Share of finished production that was scrapped. bad finished units ÷ (good + bad) × 100
Finished scrap $
The labor already spent making units that were then thrown away (material cost of the scrap is not included yet). bad units × labor $/unit
Component scrap (count)
Wasted components — individual tea bags or envelopes, not finished packages. A different unit of measure, so it's shown as a raw count only and never mixed into a finished-good scrap %.
Machines & data notes
Machine / stage
Each production stage is treated as a machine (WeighRight, AMS, Maisa 1, Maisa 2+3, Assembly, Blending). Costs roll up per machine.
Blending · LB / SB
The blending stage split by blender (large-batch / small-batch). Blending is base-level (raw blend codes), so it's reported separately and not added into finished-good costs — we don't yet have the recipe map linking a blend to a finished product.
Labor basis [std] / [n/a]
A tag meaning that stage's cost was estimated from the standard rate because it lacked operator counts to compute an actual. A transparency flag, not an error.
Mis-dated year(s)
Rows with a date typo (e.g. a "2029" or "1900") in the source. Flagged and excluded from date-filtered views rather than silently dropped.

🌀 Blending — cost to make each bulk blend (BBP)

Cost to blend one pound = blend-hours × the all-in active-blending rate (/hr). LB = large blender (~2,000 lb batches), SB = small batch. Does not yet include the “rest” of blending cost (cleaning, raw-material gathering, setup). Base-level: not added to finished-SKU cost — needs a recipe map (which blend + lbs per finished unit).
